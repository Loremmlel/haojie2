# 可缓存的单向记忆实验

这是 PR #19 合入后的独立网络结构实验，基线为
`0cc969c7bb0720602eb6b01d50102c6c5502c75c` 的 `entity-transformer-v3`。
生产训练、GUI、Rust/TS 规则和公开协议没有接入此结构。实验复用同一组模型参数，
没有优化器更新，也没有训练或评测棋力。

## 2026-10-21 CPU 实测

主机为 AMD EPYC 9V74、8 核有效配额，Python 3.12.14、Torch 2.14.0+cpu；
以下均固定 FP32、四个算子线程、一个算子间线程，数值与完整身份见 [results.json](results.json)。
模型为 width 384、6 层、6 头、FFN 1536、11,695,874 参数。

| 经典、神龛晚盘各一局至终局   |    529 |   62 | 467 / 529，88.28% |       553 / 207 |
| 两种规则自然开局各 32 条命令 |     83 |   46 |   37 / 83，44.58% |          33 / 7 |

| ---------------- | ------------: | ---------------: | -----------: | ---------------: |

晚盘 readout 缓存版相对生产 v3 的推理吞吐为 **2.622 倍**；
同一 readout 图开启缓存则为 **3.579 倍**。active 两个比值分别为 1.233、2.305 倍。
晚盘 readout 三次原始总时长为 `7.804 / 7.770 / 7.634` 秒，
v3 为 `20.285 / 20.798 / 20.372` 秒。开局缓存版为 `0.559 / 0.593 / 0.516` 秒，
v3 为 `0.483 / 0.482 / 0.494` 秒；短轨迹的相对波动更大。

晚盘逐请求计时按冷、热分别取三次中位：v3 冷根合计 2.175 秒、同根后续 18.190 秒；
readout 缓存版分别为 3.162、4.551 秒。缓存节省来自后续请求，首次建库更贵。
这个轨迹中，active 每次平均更新 161.9 个动态查询，readout 为 24.7 个；
两者读取的原始历史一样完整。合并日志追加与动态查询后，readout 晚盘总耗时从初版的
8.752 秒进一步降至 7.770 秒；初版数据与冻结源码仍保留在本地实验产物中。

两个 scope 各自对齐全部 612 条真实请求，FP32 最大 logit 差为 `1.53e-7`。
小型检查覆盖多条追加、近期窗口变化、前缀变化、根/内容/权重/精度失效、输入输出所有权，
以及旧日志影响当前读出和参考梯度。批参考的 B1 / 混合 B8 最大输出差为 `2.91e-7`。

### 前向与反向计算成本

下表每项处理相同的 16 条输入，即两个真正的 B8；三轮交错计时取总耗时中位。
无 optimizer step，所有参数梯度有限且权重保持不变：

| 结构              | 晚盘前后向 |      相对 v3 | 开局前后向 |  相对 v3 |
| ----------------- | ---------: | -----------: | ---------: | -------: |
| v3 selected-value |   1.775 秒 |     1.000 倍 |   0.164 秒 | 1.000 倍 |
| active            |   3.411 秒 | **1.922 倍** |   0.247 秒 | 1.507 倍 |
| readout           |   2.596 秒 | **1.463 倍** |   0.169 秒 | 1.033 倍 |

这是实验布局已准备好的计算成本，计时口径详见下面复现说明。它表明缓存加速推理，
训练端更深的记忆计算仍需付费，不能把 2.622 倍推理吞吐当作训练吞吐。

### 完整周期的条件估算

此前 v3 两次 CPU 完整周期的平均值为：推理 20.268 秒、更新 15.139 秒、
其余 1.282 秒，合计 36.688 秒；推理占完整周期 55.24%。
将本次推理倍率 S 与前后向倍率 r 代入 `I/S + r*U + O`：

| 假设                                         |      估算周期 | 同时间周期数 |
| -------------------------------------------- | ------------: | -----------: |
| readout，更新费用保持原来水平                |     24.151 秒 |     1.519 倍 |
| readout，更新费用增加 25%                    |     27.936 秒 |     1.313 倍 |
| readout，以前后向探针的 1.463 倍代入更新阶段 | **31.154 秒** | **1.178 倍** |
| active，以前后向探针的 1.922 倍代入更新阶段  |     46.810 秒 |     0.784 倍 |

这些是预算估算，没有运行新结构的完整训练周期。真实轨迹分布、optimizer、组批和调度
都可能改变比例。当前 CPU 负载中，readout 允许更新阶段最多增贵约 82.8% 才仍有吞吐收益；
active 仅允许约 25.3%。按 readout 的 1.178 倍周期数估算，要靠额外数据补偿，
新结构的样本效率需保持原来的约 84.9% 以上。这里的样本效率阈值不代表胜率损失。

当前取舍：readout 值得在有 GPU 的训练环境继续做同墙钟棋力比较；active 原型的更新费用
超过本次推理节省，不适合直接替换默认网络。后续首先考虑减少训练端历史重算、
为短输入选择同结构无缓存路径，以及把多流缓存查询接入实际 CUDA 组批。
这次没有 GPU 测量，不把 CPU 倍率外推为 CUDA 倍率。

## 注意力关系

采用 Prefix-LM 式分块单向关系。固定局面的实体内部保持双向，时间先后只约束 MC 日志：

| 查询来自     | 固定局面与稳定 global | MC 日志          | 当前动态查询 |
| ------------ | --------------------- | ---------------- | ------------ |
| 固定记忆     | 全部                  | 不可读           | 不可读       |
| 第 i 条日志  | 全部                  | 自身与之前的日志 | 不可读       |
| 当前动态查询 | 全部                  | 全部已有日志     | 全部         |

固定记忆包括全部有效基础实体和一个将 `globals[31]` 清零的稳定 global。
当前 global 保留真实的 prefix 标志；策略和价值均从当前动态读出计算。
所有亡者和有效日志逐项保留，没有截断、池化或把历史梯度 detach。

提供两种动态图，参数量相同：

- `active`：全部生产活跃实体、当前动作前缀/参数/路径、最近 16 条有效日志、
  全部有效候选 source/target。固定实体及日志可能同时有记忆表示和动态副本。
- `readout`：仅复制当前动作前缀/参数/路径、最近 16 条有效日志和全部有效候选引用，
  其余固定实体只作为记忆。它保留信息，减少随当前日志重新更新的实体数量。

两种模式的最后一层均只更新 global 与评分实际使用的 source/target；
全部动态实体仍提供最后一层 K/V。生产 v3 的短输入可能使用完整末层，
因此与 v3 的比较是整条结构及执行路径比较。相同 scope 的 `reference` / `cached`
才是隔离 KV cache 效果的对照。

## 缓存与失效

每个采样流独立缓存当前根的逐层 K/V，共享只读模型参数。
根键为 `(slot, generation, task, model, command_index, actor)`。
即使根键相同，也精确核对固定实体、类别、mask、稳定 global 和已有有效日志前缀。
固定区变化、旧日志修改或缩短、权重版本、设备、dtype/autocast 变化均重建。
模型必须处于 `eval`，缓存路径只用于推理。

新日志与当前动态查询在每层合并计算；日志查询禁止读取更晚日志及动态区，
只有新增日志的 K/V 写入缓存。冷启动包含固定区和已有日志的完整编码，
不会把首次计算成本从基准中拿掉。缓存原始输入快照独占存储，允许调用者复用输入缓冲。

## 复现

使用仓库的 Python 3.12 / Torch 2.14 环境和正式 Rust 引擎。在仓库根执行：

```bash
python scripts/training/benchmarks/causal_memory/check.py

python scripts/training/benchmarks/causal_memory/capture.py \
  --engine artifacts/native-target/release/haojie-engine \
  --output-dir artifacts/causal-memory \
  --mode both --natural-commands 32 --threads 4 --deadline 180

python scripts/training/benchmarks/causal_memory/bench.py \
  --trace artifacts/causal-memory/late.pt artifacts/causal-memory/natural-32.pt \
  --output artifacts/causal-memory/inference.json --threads 4 --trials 3

python scripts/training/benchmarks/causal_memory/updates.py \
  --trace artifacts/causal-memory/late.pt artifacts/causal-memory/natural-32.pt \
  --output artifacts/causal-memory/updates.json --threads 4 --trials 3
```

采集器调用生产控制器的初始化和采样，禁止覆盖已有轨迹。晚盘使用仓库的真实起点 0、2，
经典与神龛各完成一局；自然开局各运行 32 条命令，保留预算截断事实。
保存完整有序的公开输入张量，不保存 Session 或规则 RNG 状态。
采集数量与生产计数、同根不变量、采样前后权重 hash 都有检查。

采集使用固定随机初始化的未训练参数；重放固定全部请求，不让不同结构的输出改变路径。
推理重放为 CPU FP32、batch=1。每种模式以独立进程运行，同一组初始参数和完整请求，
交错三轮并取总耗时中位数。预热后重新建立空缓存，计时包含 CPU 布局/缓存检查、
冷启动、日志追加、前向和结果返回。所有请求的 reference/cache 输出逐项对齐。
`--device cuda --precision bf16` 可供另行测量单请求延迟，不代表已实现生产 CUDA 批调度。

`updates.py` 每条轨迹等间距取 16 条真实输入，形成两个真正的 B8。
生产侧用 `selected_value`，实验侧用同图的批参考，均只评分同一个已选候选并计算价值头。
损失使用 MC-Q 公式，固定 ±1 替代标签只用于构建计算图，不是棋力监督。
两种 scope 的 B1 和混合长度 B8 输出先与单请求参考对齐。
计时包含前向、损失、反向；CPU 布局准备、梯度清零、optimizer 和数据池调度不在其中。
实验的活跃集合与读取索引已预先准备，v3 内部的 `history_queries` 和候选 gather 仍在计时内。
没有 optimizer step，权重 hash 始终不变；这个比值只能称前后向成本比。

## 棋力与训练预算的解释

缓存与同结构重算具有相同数学输出，缓存本身不减少历史可见性。
结构变化限制了固定局面和旧日志对后续上下文的重新编码；当前查询必须承担这部分关联工作。
`active` 保留更多实体级处理容量；`readout` 更依赖当前 global、近期日志和候选引用，
长回溯、复活/死亡身份引用、多条历史关系组合是优先检查的能力。
另一方面，固定记忆经过更深的编码，不能仅凭单向约束断言它必然弱于 v3。

文献没有给出这款游戏的 Elo 或胜率损失预测。相关依据是：

- [T5，§3.2 / Table 2](https://www.jmlr.org/papers/volume21/20-074/20-074.pdf)
  区分全因果与双向输入前缀；其对照支持保留无时间顺序输入内部的双向交互，分数不外推为棋力。
- [GTrXL](https://proceedings.mlr.press/v119/parisotto20a.html) 及
  [Appendix D](https://proceedings.mlr.press/v119/parisotto20a/parisotto20a-supp.pdf)
  展示因果记忆可支持复杂 RL 游戏任务，同时优化稳定性会显著影响学习结果。
- [Scaling Scaling Laws with Board Games](https://arxiv.org/abs/2104.03113)
  在 Hex / AlphaZero 中发现训练与搜索计算可以交换，但单个模型也会进入平台期。
- [Scaling Laws for a Multi-Agent Reinforcement Learning Model](https://arxiv.org/abs/2210.00849)
  在 Connect Four / Pentago 中观察到计算规模与棋力的经验关系，以及模型容量对样本效率的影响。
- [ChessBench，Appendix A.2/A.3](https://arxiv.org/html/2402.04494v2)
  的主干虽然称 decoder-only，实际没有 causal mask；其棋力不能作为纯因果结构无损的证据。

更多有效自对弈数据可能改善关联历史的学习效率，前提是实际完整训练周期更快、
更新端能消费新增数据，而且模型尚未进入容量平台期。权重更新后，旧推理缓存不能直接用于
计算新权重下的训练梯度。亡者与较早日志在 v3 只更新两层，在此实验中更新五层并生成
第六层 K/V；部分活跃实体也增加了动态副本。因此必须把更贵的前后向计算计入预算。

若原完整周期为 `T = I + U + O`（推理、训练更新、其他），推理加速 S 倍、
更新时间变成 r 倍，则 `T_new = I/S + r*U + O`。
只有 `I*(1 - 1/S) > (r - 1)*U` 时，同样时间才能完成更多同等规模周期。
若吞吐变成 R 倍，样本效率相对原模型为 q，粗略补偿条件为 `R*q >= 1`；
它是预算边界，不是 Elo 预测或 RL 收敛保证。

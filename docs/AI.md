# 浩劫 2.1 · 本地AI

## 已实现的算法，不是联网模型

所有难度共用独立的`src/ai`，不调用API，不下载模型，不修改抽牌概率、数值或可操作的棋子能力。人类与AI使用相同`applyCommand`，AI只提交命令。候选生成使用引擎的ActionSpec；所有最终候选仍通过完整规则结算验证，评分函数不承担合法性判断。

| 难度 | 决策方式                                                       | 默认工作量目标                              |
| ---- | -------------------------------------------------------------- | ------------------------------------------- |
| 简单 | 单步排序、完整攻击操作延伸、接近候选间确定性扰动               | 束宽1；100次模拟/决策，1200次/回合          |
| 中等 | 窄束回合内搜索、同目标跨单位集火延伸、局面去重                 | 束宽2，最多5层扩展；320次/决策，3200次/回合 |
| 困难 | 窄束搜索，约40%自身搜索、60%回应预算；两条候选最多两轮成对回应 | 束宽2，最多7层扩展；800次/决策，8000次/回合 |

不再把“困难更宽”当作更强的依据，也不保证每个局面都比中等更深。以上是目标额度；局面结束、无有效扩展可提前停止，完整概率枚举和合法收尾可能小幅超出。`stats.depth`现在记录实际搜索过的最长己方命令链，`selectedDepth`记录选中计划的长度；完整连射/集火宏可使它超过束扩展层数。这些都**不是完整回合数，也不是对抗搜索深度**。缓存命令明确标记`cached`，零模拟不表示重搜失败。

困难回应是受限的窄贪心策略，不是全宽minimax/MCTS。候选先合法完成己方余下行动，再模拟对手完整回合；强制反应按真实决策所有者处理。对两条候选使用相同的公开随机场景编号，降低不同抽牌样本造成的比较噪声；仍然只是少量样本估计，不是完整概率树的精确期望。

只有**一整轮中两条候选都完成到共同回合边界**，才发布这一轮均分；第二轮中断时保留完整第一轮，不把半回合静态分混进来。`replies`是完成的候选回应轨迹数，`replyCandidates`和`replySamples`分别是实际采用的候选数和成对轮数，不能再拿前者冒充“已采用回应”。一轮也没有完成才退回自身搜索结果。

`begin`的计划只含阶段切换本身；进入play后重新规划，避免在summon阶段缓存整回合、绕过行动阶段回应检查。随机分叉和反应会截断确定性连招；缓存仍逐条检查真实指纹，不为了提高命中率放宽安全条件。

## 候选、评分和组合

攻击、移动、部署、主动技能、蓄力、施法、装备、合成、改判及强制反应都有候选入口。多步技能补齐目标/落点/行列/阵亡记录后才成为Command。移动与部署先用路径、占位和站位价值筛选；每个角色/能力家族保留若干候选，避免全部搜索额度被同一种部署方案占满。准备性技能也保留，因此束搜索能找到死吧！→冲锋号令→攻击的三步组合。

评价包含基地生命和可执行威胁、随从有效战力、射程与位置、装备/蓄力/关键被动、剩余操作、手牌与期限、人头、部署行、延迟危险和虹吸。死亡反击、金身、武器等的真实交换结果来自规则引擎，不写第二套伤害结算。攻击概率与特例数值由`catalog.ts`的`COMBAT_RULES`和纯函数`engine/attack-profile.ts`统一供规则结算与AI读取；`passives`和`cardValue`仍是AI策略效用，不是第二套棋子属性表。评价仍是启发式，可能估错长远价值；特别是大规模克隆、很多持续效果和多回合铺垫，不能宣称已被穷尽搜索。

束内去重忽略战报和事件等非战略字段，保留占位、技能状态、连锁关系和身份。规划结果包含公开局面指纹与命令序列；实际结果匹配时可复用确定性前缀，否则丢弃后续计划并重新计算。随机节点不选择最幸运分支来当作已知未来。

## 随机性与公平边界

`observe`按白名单复制双方公开状态，移除真实`seed`、`rng`、日志、事件及未列入的字段；Worker只接收该Observation，不接收完整Session。双方手牌本来公开，所以AI可以看到公开手牌，但看不到下一张牌或下一次骰子。

引擎新增可选的第三参数随机源，仅在假想状态的命令结算中使用，放在可释放的WeakMap中，不写进存档。普通对局没有提供该参数时，仍使用原来的可悔棋PRNG。

随机调用标注概率分界。少量概率分支在预算内逐一枚举，再按概率计算局面期望；例如冲锋怪攻击30血敌人，击杀概率是1/3，绝不会把平均30伤害作为100%击杀。分支多的召唤或复杂随机连锁采用有限分层采样，不会给每个候选读取真实随机数。第一个随机点分层，后续点独立取样；随机源来自公开局面/候选或成对场景的稳定哈希，不反推实际PRNG。

这是规则层的信息隔离，不是防作弊网络安全边界。用户可以导出自己的单机存档；本项目不试图隐藏存档或阻止用户修改自己的游戏。

## 浏览器预算和退出

浏览器与CLI默认都使用`mode: work`：工作量由公开局面、难度和已消耗的模拟数决定，不由机器耗时决定。相同Observation、难度、有效预算、算法版本得到相同决策；墙钟和UI展示延时仅作遥测/调度。预算分配忽略已花费的毫秒数。因此重放命令，与“在同预算下重算AI”是两种不同、都可检查的复现方式；重新载入后若预算历史不同，也不保证分配出同一额度。

160/450/1000毫秒保留为三档延迟参考，不是work模式的截止线。固定质量和跨负载严格毫秒截止不能同时保证；慢设备/复杂局面可能超过参考值，不能把800次模拟写成保证1秒完成。CLI可显式选`--mode timed --ms 1000`；这个模式按墙钟中断，**明确不保证跨负载同一命令**。报告必须标明模式，不能用“100000毫秒”暗中假装确定性。

回合目标根据可行动单位批次数共享，同时保留逐步合法收尾下限。Worker每隔约250毫秒发送存活进度；客户端只在无进度超时或出错时降级，而不是把仍在执行的固定工作量任务误杀。进度计时不影响选招，取消仍终止Worker；协作模式和Worker执行同一Generator。

预算用完仍须合法完成回合：保留少量逐步贪心收尾额度，不能直接跳过未部署手牌或强制反应。因此整回合数值是搜索目标，不是会导致强制终止回合的硬墙。单回合超过200条自动命令时暂停并给出继续/悔棋入口；不吞掉或擅自放弃复杂状态。

单HTML构建先编译Worker，再把代码作为常量内联进主包。运行时用Blob创建Worker，完成/取消后终止并撤销URL。Worker不可用或被宿主阻止时，用相同Generator算法在主线程分片运行；每批目标约7毫秒，每个候选家族和模拟后让出调度点。单次复杂引擎操作本身不能被强行抢占，因此分片时间也不是绝对实时保证。

页面显示思考、暂停和降级状态。新开局、载入、悔棋、弹窗、组件卸载会取消旧工作；任何返回结果都要检查请求序号、当前状态引用和决策归属，不能让过时任务落子。

## 行动节奏（表现层）

AI不再每100～160毫秒连续落子。正常节奏在接手决策时至少停顿1.5秒；一般操作间隔1.1秒，施法/技能/装备/蓄力等1.35秒，连续移动或部署可缩短到0.75秒。前一步有伤害数字时至少留1.4秒，召唤揭示至少1.5秒；即使只是结束攻击模式或进入行动阶段，也不能立刻抹掉上一招的反馈。这些数值是最低展示间隔，不是任何设备上的硬实时保证。

计算立即开始，与展示停顿重叠：真实计算已占用足够时间时，不会算完再完整等一遍。等待不计入AI搜索预算，所有难度共用节奏，缓存计划和Worker不可用时的分片计算也遵循同一等待逻辑。连锁的自动伤害仍由规则引擎原子结算，只在AI命令之间停顿，不把死亡效果拆成新游戏回合。

节奏模块在`src/ui/opponent/pacing.ts`，不修改评分、搜索参数、规则时钟、PRNG或存档。等待使用可取消的计时器；暂停、新局、导入、悔棋、打开弹窗、卸载都会取消旧等待，真正执行前再次校验任务序号和当前局面。界面在实际计算时显示“AI正在思考…”，计划就绪但尚未执行时显示“AI准备行动…”。减少动态效果设置只减少视觉运动，不跳过阅读间隔。

## 人机对弈与悔棋

新对局中选择人机模式、三档难度和人类阵营；可执先也可执后。AI回合可查看棋盘、暂停或悔棋，不能手动替AI落子。遇到人类所属死亡反应时暂停自动行动，等待人类选择；AI所属反应即使发生在人类主动回合，也由AI处理。

`Session.match`保存模式、阵营和难度。旧v2文件没有该字段时视为同屏双人，不改存储键、不新开局。刷新恢复人机局后继续剩余AI步骤；“暂停”只是当前页面控制状态，不永久冻结导入后的对局。

人机悔棋退回最近的人类可决策节点，连同随后AI回应一起撤销；不是只撤销AI最后一条微操作。AI自动回应超过60条命令时仍保留额外的`humanAnchor`，保证这次人类决策可撤销。重做恢复实际历史随机结果，不重新规划。悔棋后有重做分支时不立即让AI自动重放；点击继续AI则明确丢弃重做分支，重新规划。

## 验证与局限

`tests/ai`覆盖可观察局面隔离、真实状态不变、概率分支、确定斩杀、技能连招、对手回应、全部能力候选、强制反应、真实回合推进、设置存档和人机悔棋。`tests/browser/ai.mjs`直接验收发行HTML中的内联Worker、三档开局、暂停、旧任务取消、人类反应、刷新恢复、降级和宽度断点。默认使用断网的file://；沙箱仅渲染模式必须在报告中注明，不能冒充完整离线加载/持久化验收。

可用`npm run bench:ai -- medium,easy`或`hard,medium`做固定种子、交换先后的对局采样；`AI_BENCH_QUICK=1`只跑种子7，`AI_BENCH_PLIES`可设置回合上限。它使用固定模拟节点预算而非UI墙钟预算，便于检查策略稳定性，不是实际设备延迟测试，也不等于Elo测量。达到回合上限记为未决，不能按血量擅自改判胜者。

三档区别在计算范围、候选数、概率采样和对手回应，不是保证困难每一局都赢中等。小样本对战不能证明统计显著棋力顺序；尚未做大规模平衡验证。未来可继续校准评分与搜索，或在这些接口之上评估MCTS，而不是重复实现所有棋子规则。

## 模块与扩展

`observation.ts`负责公开信息边界；`candidates.ts`负责候选抽象；`evaluate.ts`负责启发式；`simulate.ts`负责随机分布；`search.ts`负责规划；`difficulty.ts`集中参数；`worker.ts`与`client.ts`负责运行环境适配。`src/match`单独处理对战设置与人机历史，规则引擎不读取React或Worker。

宿主导入公开React入口可传`initialMatch={{mode:'ai', human:1, difficulty:'medium'}}`。标准构建包含内联Worker；宿主自己打包源码、没有注入Worker常量时自动采用分片模式，不请求第三方脚本。`storageKey={null}`的宿主若自行持久化设置，应同时保存自己传入的initialMatch；原`onStateChange`回调保持只传GameState的契约。

技术参考：[MDN Worker](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)、[esbuild build API](https://esbuild.github.io/api/)。这些说明浏览器和构建机制，不是本项目棋力的证据。

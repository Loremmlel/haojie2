# 整局复制与状态分支重构验证

## 结论与范围

用户指出大量整局复制后，探索阶段直接验证是否能通过状态共享减少复制成本。起点为 `859cb27`，没有叠加前一轮的移动批量准备、阶段检查前移或编码缓存。探索时正式源码及发行 HTML 未改；试验代码、冻结二进制和原始结果位于 `artifacts/training/state-sharing-20260927/`。随后按用户要求接入 TS 生产引擎和 Rust 原型，当前验收进度见下方“生产接入”。

**用户最终约束：TS 与 Rust 必须保持算法一致，Node 性能下降可以接受。** 不能因为单端收益不同而让 Rust 使用共享、TS 保留原复制路线；只有一方语言确实不支持才允许有明确依据的例外。该约束已写入根目录 `AGENTS.md`，覆盖本文早期按单端性能选择方案的建议。

**可以优化，当前证据支持重构双方共同的状态分支算法。** 先前独立 Rust 原型的 1.42/1.44 倍收益及 TS 通用草稿慢约 23% 的数据仅作为历史探索证据。它们的复制粒度和适用范围不同，不能作为正式的双端方案。后续统一原型见下节，重新验证和计时；不以 Node 性能下降为由淘汰。

这是在已有 Rust 基线上继续提速，不能与之前 Rust/Node 或查询优化的倍率相乘。仍不是棋力证据，也未通过累计 30 天训练经济性门槛。

## 双端统一原型

新版源码为 `aligned/` 和 `native-aligned/`。它们都使用以下算法，不设置 TS 专有的旧算法回退：

| 环节         | 双方共同算法                                                        | TS 对应                 | Rust 对应                        |
| ------------ | ------------------------------------------------------------------- | ----------------------- | -------------------------------- |
| 只读准备     | 保持原规则与原判断顺序                                              | `transition` 原预检     | 原命令准备函数                   |
| 分支根       | 复制标量和实体引用列表                                              | `forkPosition`          | `State::fork`                    |
| 棋子与地标   | 每个实体作为一个复制单元，写入时隔离完整实体子树                    | 实体所属草稿与 `detach` | `Unit::fork`、`Rc::make_mut`     |
| 其他局面字段 | 按顶层字段作为复制单元                                              | 顶层字段所属草稿        | `ValueMap::fork`、字段可变访问   |
| 小型核心容器 | turns、bases、deployRows、pending、siphons、events 在分支创建时复制 | `ownedFields` 对应集合  | `State::fork` 同名字段的 `clone` |
| 规则内部快照 | 继续复制独立数据，不把这一项仅在 Rust 改成共享                      | `cloneRuleData`         | `Unit::clone`、普通 `Clone`      |
| 正式成功     | 导出独立拥有型快照，禁止外部持有内部草稿                            | `clonePosition(next)`   | `next.clone()`                   |
| 预检与失败   | 预检只返回状态，失败不提交；整个分支丢弃                            | 原预检与异常边界        | 原预检与 `Result` 边界           |

引用管理方式属于语言实现机制：Rust 在可变借用时按需取得独立数据，TS 通过来源表区分输入对象与分支新对象，再拦截写入。它们不能改变上表的复制单元、正式/预检适用范围或提交策略。Node 不因较慢而改用另一条算法；当前没有声明语言不支持的例外。

统一 TS 的首版差分发现投石标记的对象身份错误：新建效果被包装后，按引用删除未命中。修复的是写入层的新对象身份，规则未修改。旧失败 bundle、来源哈希和源文件片段保留在 `aligned-v1*` 与 `ts-aligned-validation/`。最终版本通过 1101 场景/31990 条命令的预检、完整执行、输入不可变和正式输出可原生 `structuredClone` 检查；没有 Proxy 泄露到公开快照。Rust 统一版也通过 1101 场景/31990 次预检与正式执行、2202 根/5232 节点。

统一版各自与冻结基线比较，每种模式 1000 命令，预热后三轮交错中位数如下：

| 统一算法 |             经典：基线→原型 |             神龛：基线→原型 |
| -------- | --------------------------: | --------------------------: |
| Rust     |         6.413→4.888s，1.31× |         9.667→7.080s，1.37× |
| Node     | 11.105→14.655s，耗时 +32.0% | 13.135→17.783s，耗时 +35.4% |

来源为 `aligned-games-1000/summary.json` 与 `ts-aligned-games-1000/summary.json`。两端各自的选招、8 项工作量、完整终态和双方观察均与原 TS 参照相同；Node 另核对全部访问节点、编码和 logits 的摘要。Node 回退按用户约束接受，不保留单端旧算法。两批执行时间不同，不据此拼接新的 Rust/Node 倍率；下面旧独立原型的倍率和分配数据不能移用。

统一版长局验证已完成：Rust 从种子独立选择经典 4591 条、神龛 8679 条命令，分别达到 171/257 ply 的自然终局，全部选招与原 TS 记录一致；统一 TS 逐条重放时，每一步完整状态都与冻结原 TS 相同。两端最终权威局面、双方观察、终局状态及 8 项工作量一致。没有向原生选招器提供参照命令，没有把长局功能验收耗时作为交错性能结果。

## 为什么需要复制，哪些可以省

现有流程用完整副本保证两件事：模拟分支不修改输入；命令执行中途失败时，已支付的资源、随机状态、伤害与反应均不泄露到原局面。直接删掉 `clone` 会破坏这些契约。

但预检调用同一套规则，只返回合法、非法或遇到随机的状态，并不保留执行后的局面。此前诊断每 1000 条实际命令，经典/神龛分别触发 25441/27907 次 `State::clone`。这些分支大多只需要读取多数棋子、修改少数实体，提前复制全部内容的代价可以避免。

用户明确最终约束之前，先分别测试了三种方案；这部分记录保留为历史证据：

1. **Rust 棋子共享**：`Unit` 内部用 `Rc<UnitData>`，读取保持共享，首次可变访问由 `Rc::make_mut` 复制。局面中的棋子列表仍复制引用，战斗中临时棋子快照也变为共享。规则使用原来的字段与函数。
2. **Rust 棋子＋字段共享**：在上一步上，局面扩展字段按顶层键共享各自的 JSON 子树；例如只修改手牌就无需复制死亡记录和时钟快照。保留键顺序、序列化结构和移除语义。另避免举旗同步中“删除本来不存在的字段”触发全部棋子的复制。
3. **TS 预检草稿**：正式入口仍使用原副本；预检改用分支独立的 Proxy 草稿，对象第一次写入才浅复制。规则内部快照改用可读取草稿的纯数据复制入口，防止原生 `structuredClone` 拒绝 Proxy。它是隔离原型，不是可发布的通用事务库。

没有跳过结算、删掉事件/日志/兼容字段、使用平均随机结果或缩减候选。Rust 的引用计数仅用于当前单线程采样；线程间共享状态需要另行设计和计时。

Rust 正向原型相对基线只修改 10 个文件，增加 96 行、删除 15 行，包括 Cargo 依赖声明、状态容器和几处借用写法。这个范围说明本次收益可以集中在状态层取得，尚不需要把全部棋子规则重新实现。

## 建议重构的边界

保留外部 `applyCommand` / `inspectCommand` 协议，内部集中维护“只读准备→创建分支→原规则结算→成功提交或失败丢弃”。共享结构仅在存储层处理所有权，不把各种棋子的规则重新实现一遍。

| 方向                     | 判断               | 后续边界                                                                         |
| ------------------------ | ------------------ | -------------------------------------------------------------------------------- |
| 复制前的阶段/资源检查    | 继续实施           | 复用原规则的准备函数；此前收益约 6%～10%，不能代替状态复制重构                   |
| 分支共享、修改部分才复制 | 双端使用统一算法   | 已接入TS生产引擎与Rust原型，规则/事务/完整采样及生产验收通过                     |
| TS 通用 Proxy 草稿       | 由统一粒度原型替代 | 不因 Node 较慢而改回另一算法                                                     |
| 显式写入接口             | 双端后续共同候选   | 若更换写入接口，对应调整两端；不能只有一方改变复制粒度或事务流程                 |
| 执行后回滚的撤销日志     | 本轮未实现，不先选 | 必须覆盖嵌套写入、队列、数组删除、序号、随机状态和异常；遗漏一项就会污染后续分支 |
| 重写全部规则算法         | 当前不支持         | 已测收益来自复制方式，尚无证据证明重新实现全部规则更划算                         |

TS 和 Rust 必须保持相同的分支算法、事务生命周期、预检条件与结算顺序，并维护实现对应表，不能只靠结果相同宣称算法相同。语言的引用管理机制可以不同。双方正式提交均导出独立快照，TS 不能直接返回共享的可变普通对象或 Proxy。公开 JSON 往返和编码成本等后续优化也遵循同一约束。

统一算法已接入双方状态容器，生产回放与浏览器验收见上文。后续共同落地只读准备与参数批量检查。性能报告分开列出两端结果，Node 性能下降不单独否决方案。随后重测残余成本，若进一步类型化状态或修改编码接口，也维护双端对应算法。最后单独复核自然终局、并行、记录出口与中断恢复的累计 30 天经济性。

## 证据与复现入口

实验目录中的源码副本不参与构建或部署，原轨迹只读。运行时创建新的输出目录，禁止覆盖历史结果。

- `aligned/`、`native-aligned/`：统一算法的最终双端源码副本。
- `aligned-validation/`、`ts-aligned-validation-v3/`：统一版的规则、正式输出和候选节点差分。此前 v1 的失败与 v2 的中间版本保留，不覆盖。
- `aligned-games-1000/`、`ts-aligned-games-1000/`：统一版三轮交错连续采样。
- `complete-aligned-games/`：统一版两场自然终局；额外逐步核对统一 TS 与原 TS 的全部 13270 条命令后状态。
- `frozen-aligned/`：4 个驱动的冻结依赖图、77 个来源文件哈希及工具链信息。

以下为早期独立探索证据：

- `native-units/`、`native-shared/`：两个 Rust 原型；`units-validation/`、`shared-validation/` 保存差分结果和来源哈希。
- `units-games-1000/`、`shared-games-1000/`：不带诊断探针的三轮连续采样。
- `draft/`、`draft.mjs`、`ts-draft-validation/`：TS 草稿源码、冻结依赖图与规则差分。
- `ts-draft-roots-32/`、`ts-draft-roots-128/`：公开局面筛查，保留负结果；各轮实际顺序为基线先运行，不能称作交错计时。
- `explore-paired.ts`：修正两个方案“轮转后又反转，抵消交错”的计时顺序，用于本轮连续采样；既有筛查文件不改写。
- `ts-draft-games-1000/`：早期 TS 三轮连续采样，候选、张量、logits 和最终状态一致，性能负结果保留但不作为否决理由。
- `native-profile/`、`allocations/`：单独的分配诊断源码、冻结二进制和完整计数。
- `complete-games/`：两场独立原生自然终局，与 TS 全部选招、完整状态及双方观察核对。
- `frozen/`：6 个驱动的冻结依赖图、127 个来源文件哈希、Cargo 清单/锁、CPU、Node 和 Rust 版本。Rust 包继续复用已锁定的 indexmap 2.10.0，只增加直接引用和 serde 的 rc 功能。

```powershell
cargo build --release --locked --manifest-path artifacts/training/state-sharing-20260927/native-aligned/Cargo.toml --target-dir artifacts/native-aligned-target
npx tsx artifacts/training/state-sharing-20260927/native.ts --output aligned-validation-rerun --candidate aligned --executable artifacts/native-aligned-target/release/haojie-engine-prototype.exe --validate
npx tsx artifacts/training/state-sharing-20260927/native.ts --output aligned-games-rerun --candidate aligned --executable artifacts/native-aligned-target/release/haojie-engine-prototype.exe --rounds 3
npx tsx artifacts/training/state-sharing-20260927/explore-paired.ts --variants 'baseline,aligned' --output ts-aligned-games-rerun --games --rounds 3
```

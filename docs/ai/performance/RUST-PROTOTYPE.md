## 目标与边界

9月27日追加：[整局复制与状态分支验证](STATE-SHARING-2026-09-27.md)先得到独立原型的Rust 1.42/1.44倍收益和TS约23%耗时回退。用户随后明确**双端算法必须一致，Node性能下降可以接受**；据此放弃按单端速度各选一路，改做复制粒度、正式/预检范围、内部快照和提交方式一致的双端原型。统一Rust版测得经典1.31倍/神龛1.37倍，Node耗时增加32%/35%，该回退按约束接受；两场完整对局共13270条选招及状态核对通过。不能沿用独立原型的倍率或分配量，也不与历史倍率相乘。现已按用户要求同步接入TS生产代码与Rust原型：404项行为测试、双端71955条历史命令、2202根5376节点、重新独立采样的13270条完整对局命令及训练记录出口均通过；九组浏览器验收、类型/格式/目录、Rust静态检查及833324字节发行HTML一致性通过。最新证据位于 `artifacts/training/state-sharing-integration-20260927/`，本轮不更新正式性能倍率，详见专项文档。

本轮验收范围为公开候选树、编码、小网络与完整采样，继续核对底层规则和连续整局。实现、规则一致性、采样速度和训练经济性分别报告。

最终目标仍为浏览器端侧神经网络＋搜索对强人类胜率超过50%；现有机器累计训练预算30天，可中断。浏览器继续使用 TS。本文管理独立的原生训练引擎原型，不将吞吐、规则一致性或自对弈结果混作棋力证明。

原型从移动切片逐步扩展到完整规则。保留 TS 的阶段校验、四向遍历顺序、分数移动蓄力、2×2、叠放、独行侠禁区、继承能力、事件和部署行语义。数值图鉴、`COMBAT_RULES`、召唤池和合成配方由 TS 导出，Rust 不维护第二份数值表。兼容和扩展字段原样保留。

未知能力仍须明确失败，不能伪装成非法候选或回退 TS 计作 Rust 成绩；完整验收不再跳过 `unsupported`。Rust 选招移植同一公开动作树，不增加另一套策略评分；权威 seed/rng 只供规则结算与完整状态差分，绝不接入网络或搜索输入。当前剩余范围以第五阶段为准。

## 预先约定的验收

1. Rust 可编译运行；协议版本、规则版本不符明确拒绝。依赖锁定，构建产物留在忽略目录。
2. 用经过共享读取器验证的现有轨迹重建局面；逐命令比较支持范围内的完整状态，包括事件、序号、随机状态、兼容字段。原文件与历史指纹不改写。
3. 对固定真实局面和专项局面比较全部117格预检结果、错误原因、路径及完整结算；验证非法输入不改变旧局面，列出不支持比例。缺少终局的轨迹仍是 unknown。
4. 串行预热后至少3轮交错计时，工作量和返回值一致。分别报告本地核心计算、常驻进程的完整请求（序列化、传输、解析、计算、输出），不扣除通信来宣称端到端收益。
5. 若原生计算中位加速不足2倍，停止扩大切片，先定位表示/复制成本。若计算通过但通信不通过，只能证明应将批量工作留在 Rust，不能推荐每次查询跨进程。这是原型工程门槛，不是30天经济性门槛。
6. 即使以上通过，仍需后续完整规则、随机/反应差分与完整采样闭环，才可重判训练经济性。

### 性能

Ryzen 7 5800H、Node 22.23.2、Rust 1.98.1 release，串行预热后3轮交错，中位数。每种真实轨迹均匀抽8个支持的移动根，共32个。批量查询每根含全部117格和5项边界检查，共3904个预检，再执行一条实际命令；另一组只执行相同32条实际命令。两端工作量与输出逐项相等。

| 工作量                      |   TS 核心 | Rust 核心 | 核心倍率 |
| --------------------------- | --------: | --------: | -------: |
| 32根批量查询＋结算，重复5轮 |  794.17ms |  170.74ms |    4.65× |
| 32条结算，重复100轮         | 1132.67ms |  426.37ms |    2.66× |

另测一批完整请求，包含局面与命令的序列化、管道传输、Rust解析/执行/序列化以及 Node 解析：

| 工作量               | TS 直接调用 | TS 同样 JSON 输入/输出 | Rust 完整进程请求 | 相对 TS 直接调用 |
| -------------------- | ----------: | ---------------------: | ----------------: | ---------------: |
| 32根批量查询＋结算   |    160.27ms |               180.01ms |           89.34ms |          快1.79× |
| 32条结算，无候选查询 |     10.80ms |                27.28ms |           48.09ms |          慢4.45× |

核心门槛通过，**逐次传送完整局面替换 TS 结算的集成方式不通过**。常驻进程本身不能消除 JSON 和整局传输成本；后续必须让状态、候选查询和一段连续执行留在 Rust，再测真实采样闭环。表中均为移动切片，没有网络推理、搜索树、完整自对弈、GPU优化器或多进程训练。

倍率也不是纯粹换语言的收益：Rust 用有类型的移动字段、固定117格访问表和返回值错误，并仅投影 `getStats` 中移动入口读取的字段，省去了攻击属性/攻击光环计算。规则公式、候选范围、路径顺序及结果保持一致；没有引入另一套策略评分。两端维护对应关系见 [原型说明](../../../native/engine-prototype/README.md)。

## 第二阶段：攻击、反应与驻留局面

### 已实现范围

增加攻击路径与入射方向、完整属性与虹吸刷新、非穿透攻击、分份伤害、暴击/免疫随机、按来源消耗名刀、死亡/人头/衍生物、反击/反伤、冲撞/弹出，以及小屋/王城、死后射击、反射、命中牵引等反应。图鉴与随机攻击参数从 TS 注入，正式 RNG 使用相同 xorshift32 分界与消耗顺序；预检到需要随机值时返回 `uncertain`。

协议升级为 `haojie-native-engine-v2`，增加 `reset / step / export`。一次装载后可连续发命令，不必每步传回完整局面。整批先解析，执行时逐条提交；过期修订号、结构错误不执行，规则非法或未支持时停止在最后成功前缀。是否清除日志/事件显式指定，默认保留；训练差分使用与 `TrainingEnvironment` 一样的逐步清理。

新增驻留协议验证通过：保留/清理历史两种模式、陈旧修订号、错误重置、批次后项解析失败、合法前缀后遇非法命令、失败后续接，以及攻击已经消耗 RNG 并造成伤害后再遇到未移植能力的完整回滚。`trace` 只为差分返回每条命令清理前状态，计时不传这些中间状态。

扩展真实回放发现并修复两处跨语言差异：

- `shrine-uniform/worker-3`：投石机击杀满血目标后缺失标记事件、`serial` 少1。Rust 在目标离场后错误读取攻击前的满血快照；已修正并增加普通单位、死亡衍生物和地标3个专项。
- `shrine-uniform/worker-5`：金晔地标击杀普通棋子后，Rust 额外增加 `kills`。TS 的击杀奖励/强夺只查普通棋子层，Rust 使用了含地标的通用查找；已对齐层范围。专项采用敌方棋子移动到地标同格的合法情况（金晔射程为0），修复前二进制确实能复现差异。

两个原失败局面均单独验证完整状态恢复一致。失败证据分别保留在 `artifacts/training/rust-combat-20260927-full1/mismatch.json` 与 `rust-combat-20260927-full2/mismatch.json`，不把失败轮次算作整批验收通过。真实轨迹、专项枚举和连续命令验证分别报告，不混作独立对局数。

### 性能定位记录

扩展后的首次完整验收保存在 `artifacts/training/rust-combat-20260927-full3/`：支持范围内完整状态差分通过，但32个真实攻击根的原生核心仅比 TS 快1.49倍，未达事前的2倍工程门槛。32段共148条连续命令驻留执行，TS 直接调用中位68.75ms；Rust 批次执行33.65ms，计入装载和导出后为90.17ms，仍慢约31%。因此先暂停扩充规则，定位复制成本。

按 ID 查询目标时，原型先构建 `targets(s)`，深复制整盘所有单位，再只保留一个目标。攻击入口、伤害反射和虹吸刷新共用这种写法。现改为先借用状态按原先顺序查找，再只复制命中对象；状态整体复制、规则和候选范围不变。在两个冻结故障局面上交错执行3轮、每轮1000次，两版均与 TS 完整状态一致，旧版922.63ms、新版619.86ms，原生内部加速1.49倍（耗时下降32.8%）。证据 `artifacts/training/rust-combat-20260927-lookup.json`；这是定位用的两个局面，不代替真实攻击样本集或整局经济性。

### 差分中实际修复的问题

- 直线延长：Rust 浮点 `signum(0)` 与 TS `Math.sign(0)` 不同，零轴需显式保持0，不能产生斜线路径。
- 显式路径未给 `targetId` 时，目标须和 TS 一样取穿透路径的最后命中项。
- 巨大化改变单位落点后，事件的主体坐标仍须来自命令入口的目标包装；单位尺寸/身份快照按当前事实补齐。
- 技能/范围事实不能污染普通伤害事件；衍生墓地事件须明确死者主体。
- 普通20献祭/到期死亡不触发反伤；强夺在移走装备前须保存死者快照，供死后射击、反伤和持续区域使用。

### 为什么目前只快约两倍：2026-09-27性能归因

诊断基线为已提交的 `859cb27`，正式性能结论仍用上面的预热三轮数据。先核对 release/LTO 配置，再在忽略目录复制 Rust 源码，加互斥分项计时及包装 `System` 的线程内分配计数；正式源码、分配策略、候选顺序、网络计算和随机消耗不改。两种模式各用原来的1000命令，依次运行无探针、只有计时、计时加分配计数三种版本。全部命令、8项工作量、完整终态、双方观察和截断状态一致。

诊断目录为 `artifacts/training/rust-profile-20260927/`：包含 `profile.ts`、修改后的隔离源码、源码/二进制哈希、冻结的 `baseline.exe / profile.exe` 和各次JSON报告。诊断驱动为 `node --import tsx artifacts/training/rust-profile-20260927/profile.ts`；现有报告采用排他写入，复测须另建目录并按脚本调整输出，不能覆盖旧证据。计数器增加开销，桌面负载/频率未锁定；诊断时间仅用于定位，不能替换正式三轮倍率。

**已排除逐步IPC和debug构建。** 基线复测中，经典内部5287.467ms、外部5291.869ms，神龛内部7804.519ms、外部7809.345ms。差值4.40/4.83ms还包含末尾观察/导出、序列化和策略初始化等，并非纯通信；约占0.08%/0.06%。当前批次通信不是主要成本。Cargo 使用release、thin LTO和单codegen单元。本机 `node --v8-options` 显示优化编译器开启，`jitless`关闭；当前对照是已优化的V8路径，不能预设“Rust对解释器”的倍率。

**直接观察到的成本是大量预检和对象分配。** 下面均为1000条实际成功命令的固定工作量：

| 计数                         |     经典 |     神龛 |
| ---------------------------- | -------: | -------: |
| 完整合法性预检入口           |    97776 |   107912 |
| 其中最终拒绝的候选           |    86660 |    95410 |
| 整局 `State::clone`          |    25441 |    27907 |
| 公开JSON复制并转成内部局面   |     2000 |     2703 |
| `getStats`对应查询           |   185581 |   240143 |
| 堆分配/扩容调用              | 57002950 | 83925532 |
| 累计申请字节（十进制GB）     |     8.84 |    12.46 |
| 其中整局复制的申请字节（GB） |     3.57 |     5.09 |

累计申请量不是峰值内存、存活数据或物理DRAM流量；扩容按新申请尺寸计入。分配次数也不能直接换算成耗时占比。只开计时的诊断里，整局复制自身约占20%，公开局面转换约9%/12%，编码自身约13%/14%；这些是扣除嵌套探针后的分项，不能重复相加到父级的候选树计时里。复制只计构造，副本销毁在其调用方分项内。正式无探针的三轮总计仍显示候选树加编码约占84%。

代码原因有三层：

1. **保留了动态表示。** `model.rs` 的核心字段有类型，但状态扩展、效果、反应、时钟帧等仍是 `serde_json::Value/Map`，种类/身份/模式大量使用字符串。`Target::from` 还拥有棋子副本，`reserve` 为只读查询构建JSON，`Kind::key` 为查表构造字符串。Rust的深复制会复制这些容器和拥有的字符串；TS的专用复制器保留不可变标量，仅递归子对象。语言替换没有消除这些表示成本。
2. **同一公开局面重复转换和编码。** `sampler.rs` 为检查回合外巨大化先构造公开 `State`，`Tree::new`又构造一次；神龛存在额外的回合外树。每个参数节点还重建编码器、身份映射和实体数组。都是原生进程内部工作，与管道通信无关。
3. **查询次数仍被通用试执行放大。** 约一百次合法性预检才对应一条实际命令，约89%的预检最终拒绝。现有只读准备已提前拒绝很多参数，但剩余分支仍要构造副本执行规则，之后销毁或回溯。换语言不改变这项工作量；长局回溯更密集，见完整对局表。

这说明当前收益受表示、复制和查询方式共同限制；不能把“全部代码用Rust执行”当作“已完成原生数据布局优化”。本轮没有建立各项优化的单独加速倍率，也没有证明可以达到10倍或更高。

后续按用户要求先探索两端共用的查询组织方式，见[共享算法优化探索](SHARED-QUERY-OPTIMIZATION-2026-09-27.md)。隔离对照确认移动批量准备在TS有明确收益，但Rust只有约3%～5%提速；另将阶段/召唤资源检查前移到复制之前，Rust经典/神龛再单独对基线测得1.08倍/1.09倍。固定局面编码及参数公共条件也能复用，不能把TS组合倍率当作Rust已验证收益或将各项相乘。下一步共同抽取只读准备，再逐项评估参数公共条件和编码复用；按残余成本处理 `Value→State` 往返、临时JSON、字符串键及只读引用。涉及新的合法性快路径时同时维护TS与Rust，并通过旧完整轨迹和候选差分。算法和规则保持一致，不要求两种语言逐字采用相同内存布局。小网络当前只占约7%～9%，SIMD、换分配器或进一步改通信需先有针对性测量，不作为首要方向。

R9b 的功能闭环已完成。下一步 R9c 需要自然长局、并行扩展、生产记录/中断恢复成本和累计30天预算的独立复核；如经济性不通过，停止扩大训练。正式可训练模型的批量推理、优化器和搜索的可枚举随机源仍未原生接入，不能把 TinyPolicy 采样闭环称为最终神经网络＋搜索 AI，也未测量对强人类胜率。
